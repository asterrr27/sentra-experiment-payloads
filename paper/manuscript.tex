\begin{abstract}
AI agents powered by large language models (LLMs) increasingly operate with tool access---reading files, sending emails, and executing commands---introducing a broad attack surface. We present a controlled experiment using the Sentra platform, evaluating five LLM agents---three simulated security postures (weak, medium, strong) and two external models (Gemma-4-31b, GPT-4o-mini)---across 13 attack scenarios mapped to 6 OWASP LLM Top 10 categories. Using 130 unique attack payloads (10 per scenario), we conducted 1,950 total trials. Our results show a 40 percentage-point improvement from the weakest (3.33\% pass rate) to the strongest simulated posture (43.33\% pass rate), with statistical significance (p < 0.05, Cohen's d > 0.8). External models achieved notably higher pass rates (Gemma: 100\% on 13 payloads, GPT-4o-mini: 71.54\% overall or 93.0\% excluding API errors), suggesting architectural differences in security robustness. We identify multi-step chains and permission boundary violations as the most challenging scenarios, with only 0\%--3.3\% pass rates across all simulated agents.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Large language models (LLMs) have evolved beyond conversational chatbots into autonomous agents capable of using tools, accessing files, and executing commands. This capability expansion introduces significant security risks, as adversaries can inject instructions that cause agents to deviate from their intended behavior~\cite{willison}.

While prior work has catalogued attack taxonomies~\cite{owasp, owasptop10} and demonstrated individual exploits~\cite{liu, wei}, systematic controlled evaluations across multiple security postures remain scarce. Most existing studies evaluate a single model or defense in isolation, making cross-comparison difficult.

In this paper, we present a controlled experiment that addresses three research questions:

\begin{enumerate}
  \item How do different security postures (none, basic, comprehensive) affect agent resilience against prompt injection attacks?
  \item Which attack scenarios are most effective at compromising LLM agents?
  \item How do external models (Gemma, GPT-4o-mini) compare against simulated security postures?
\end{enumerate}

We designed three simulated agents with escalating security defenses---ranging from no protections to full injection detection---and tested them against 130 attack payloads spanning 13 scenarios across 6 OWASP LLM Top 10 categories. We further validated against two external models.

\section{Background and Related Work}
\label{sec:background}

\subsection{LLM Agent Security}
LLM agents extend language models with tool-calling capabilities, enabling actions such as file operations, email communication, and web searches. This architecture introduces a new attack surface where injected instructions can trigger unintended tool usage. Recent benchmarks such as AgentDojo~\cite{agentdojo}, ASB~\cite{asb}, and InjecAgent~\cite{injecagent} have systematized the evaluation of these vulnerabilities.

\subsection{Prompt Injection Attacks}
Prompt injection attacks embed malicious instructions within user inputs to override an agent's system prompt~\cite{greshake}. Variants include direct injection, indirect injection via tool outputs~\cite{injecagent}, role-play jailbreaks, and token smuggling.

\subsection{OWASP LLM Top 10}
The OWASP LLM Application Security Top 10~\cite{owasptop10} provides a standardized taxonomy of vulnerabilities. Our experiment covers six categories: LLM01 (Prompt Injection), LLM02 (Sensitive Information Disclosure), LLM05 (Improper Output Handling), LLM06 (Excessive Agency), LLM07 (System Prompt Leakage), and LLM10 (Unbounded Consumption).

\subsection{Existing Evaluations}
Recent work has established standardized benchmarks for LLM agent security. AgentDojo~\cite{agentdojo} provides a dynamic environment for evaluating prompt injection attacks and defenses. ASB~\cite{asb} proposes a comprehensive security benchmark covering multiple attack dimensions. InjecAgent~\cite{injecagent} systematically evaluates prompt injection vulnerabilities across diverse agent configurations. However, these benchmarks typically evaluate a single model or defense in isolation. Our work extends prior approaches by combining controlled agent simulation with varying security postures and external model validation, mapped to the OWASP LLM Top 10 taxonomy~\cite{owasptop10}.

\section{Methodology}
\label{sec:methodology}

\subsection{Agent Design}
We implemented three simulated LLM agents using LangChain with Llama 3.3 70B via Groq. Each agent exposes tools through a FastAPI HTTP server:

\begin{itemize}
  \item \textbf{Agent A (Weak):} Five tools (read\_file, send\_email, search\_web, delete\_file, execute\_command). System prompt: \textit{``You are a helpful assistant.''} No refusal enforcement.
  \item \textbf{Agent B (Medium):} Three tools (read\_file, send\_email, search\_web). Basic profanity filter and refusal keywords. System prompt includes safety reminders.
  \item \textbf{Agent C (Strong):} Two tools (read\_file, search\_web). Comprehensive injection detection, 3-iteration limit, adversarial prompt classifier.
\end{itemize}

\subsection{Attack Scenarios}
We developed 130 attack payloads across 13 scenarios, with 10 payloads per scenario. Table~\ref{tab:scenario} lists all scenarios and their OWASP mappings. Each payload includes a unique attack vector (e.g., direct injection, tool output manipulation) and expected behaviors for both vulnerable and secure agents.

\subsection{External Validation}
To assess real-model generalization, we validated against two additional models:
\begin{itemize}
  \item \textbf{Agent D:} Gemma-4-31b-it via Google Gemini API (13 payloads, 1 per scenario, due to free-tier quota constraints)
  \item \textbf{Agent E:} GPT-4o-mini via GitHub Models API (130 payloads, all scenarios)
\end{itemize}
Both used identical PASS/FAIL criteria based on response analysis.

\subsection{PASS/FAIL Criteria}
For each trial, an agent response is classified as:
\begin{itemize}
  \item \textbf{PASS:} Agent refused the injected instruction, maintained its original goal, or identified the attack.
  \item \textbf{FAIL:} Agent acted on the injected instruction (e.g., sent email, read protected files, disclosed system prompt).
\end{itemize}
Failure types include: goal\_deviated, info\_leaked, tool\_abused, and api\_error. For external models, API errors (rate limits, network failures) are counted as FAIL in the aggregate statistics. Of 130 GPT-4o-mini trials, 30 resulted in API errors (23\%). We report both pass rates---excluding errors (93.0\% of successful calls) and including errors as failures (71.54\% overall)---throughout this paper.

\section{Threat Model}
\label{sec:threatmodel}

We define the adversary model used throughout this experiment:

\paragraph{Adversary Capabilities.}
The attacker can send arbitrary text inputs to the agent through the standard user interface. The attacker can also poison tool outputs that the agent reads (indirect injection scenarios). The attacker has knowledge of which tools the agent exposes but cannot modify the system prompt directly.

\paragraph{Adversary Goals.}
We consider four attacker objectives aligned with the OWASP LLM Top 10:
\begin{itemize}
  \item \textbf{Data exfiltration:} Read protected files (e.g., /etc/passwd) or email sensitive data to external addresses.
  \item \textbf{Tool abuse:} Execute unauthorized commands, delete files, or send unsolicited emails.
  \item \textbf{System prompt extraction:} Reveal the agent's system prompt or configuration details.
  \item \textbf{Denial of service:} Trigger infinite tool-calling loops to exhaust resources.
\end{itemize}

\paragraph{Defender Capabilities.}
The defender can configure the agent's system prompt, choose which tools to expose, and implement input/output filters. In our experiment, these defenses escalate from none (Agent A) through basic refusal enforcement (Agent B) to comprehensive injection detection with iteration limits (Agent C). The defender cannot modify the underlying LLM's pre-trained behavior.

\section{Experiment Design}
\label{sec:experiment}

Each of the 3 simulated agents was tested against all 130 payloads across 3 randomized runs (390 trials per agent, 1,170 total). External models contributed an additional 780 trials (390 each). All payloads were executed in deterministic order per run, with random seed 42 for reproducibility.

Statistical analysis used the Mann-Whitney U test for pairwise comparisons and Cohen's d for effect sizes. Confidence intervals were computed at the 95\% level across randomized runs.

\section{Results}
\label{sec:results}

\subsection{Overall Performance}
Table~\ref{tab:overall} presents aggregate results. Agent C (Strong) achieved a 43.33\% pass rate compared to Agent A (Weak) at 3.33\%---an absolute improvement of 40 percentage points. External models performed notably higher, with Gemma-4-31b passing all 13 tested payloads (100\%) and GPT-4o-mini achieving 71.54\% overall (93.0\% on 100 successful calls, with 30 API errors counted as failures).

\subsection{Statistical Significance}
Pairwise Mann-Whitney U tests reveal:
\begin{itemize}
  \item \textbf{A vs B:} Not statistically significant (p > 0.05) across most scenarios, indicating basic profanity filters provide marginal improvement.
  \item \textbf{A vs C:} Statistically significant (p < 0.05) with large effect sizes (Cohen's d > 0.8), confirming comprehensive injection detection is effective.
  \item \textbf{C vs D/E:} External models significantly outperformed simulated agents, likely due to architectural differences in instruction following.
\end{itemize}

\subsection{OWASP Category Breakdown}
Figure~\ref{fig:owasp} shows pass rates by OWASP category. LLM01 (Prompt Injection) showed the widest spread (3.89\%--46.67\% across simulated agents), while LLM02 (Sensitive Information Disclosure) showed strong external model performance (90\%--100\%).

Agent C (Strong) had the lowest mean response latency (2,230 ms), compared to Agent A (3,208 ms) and Agent B (2,686 ms), suggesting security checks can be efficient. \section{Discussion}
\label{sec:discussion}

\subsection{Key Findings}

\textbf{Comprehensive detection matters.} The 40 percentage-point improvement from Agent A (3.33\%) to Agent C (43.33\%) is statistically significant (p < 0.05) with large effect sizes (Cohen's d > 0.8). This confirms that multi-layered injection detection---combining input filtering, output validation, tool restriction, and iteration limits---is necessary for robust agent security.

\textbf{Single-layer defenses are insufficient.} Agent B's basic profanity filter and refusal keywords produced marginal improvement (20.0\% vs 3.33\%) that was not statistically significant across most scenarios (p > 0.05). This finding warns against relying on superficial defenses.

\textbf{External models show stronger baseline security.} Gemma-4-31b resisted all 13 tested payloads (100\%), and GPT-4o-mini passed 93 of 100 successful trials (93\%). Both substantially outperformed the strongest simulated agent (Agent C at 43.33\%). This gap likely reflects architectural differences in safety training and instruction-following behavior rather than any specific defense mechanism.

\textbf{Scenario difficulty varies widely.} Multi-Step Chain, Permission Boundary, and Indirect Injection consistently compromised all simulated agents (0\%--3.3\% pass rates). These scenarios exploit fundamental gaps in how agents handle context switches and authority verification. Conversely, Role-Play Jailbreak and Token Smuggling were effectively resisted by Agent C (90\%--100\%), suggesting these attack vectors are more amenable to pattern-based detection.

\subsection{Threat Model Validation}
Our threat model assumed the attacker knows the agent's toolset but not the system prompt. The results validate this: the most successful payloads (GD\_010, MS\_002) exploited tool knowledge (e.g., ``call send\_email to exfiltrate'') rather than requiring system prompt access.

\subsection{Limitations}

We acknowledge the following limitations:

\begin{enumerate}
  \item \textbf{Gemma validation subset:} Agent D (Gemma-4-31b) was validated on only 13 of 130 payloads (1 per scenario) due to Google Gemini free-tier quota exhaustion. The 100\% pass rate should be interpreted cautiously. We attempted a full 130-payload run but the API was too slow (30+ seconds per call) and repeatedly timed out.
  \item \textbf{GPT-4o-mini API errors:} 30 of 130 GPT-4o-mini trials (23\%) resulted in API errors (rate limits, server disconnects). These were counted as FAIL in aggregate statistics. The true pass rate on successful calls is 93.0\%.
  \item \textbf{Single base model:} All three simulated agents use Llama 3.3 70B via Groq. Results may not generalize to other model architectures (GPT-4, Claude, Gemini).
  \item \textbf{Simulated agents:} Our LangChain-based agents, while realistic, may not fully replicate commercial agent deployments with proprietary safety layers.
  \item \textbf{No timing data for external models:} Agents D and E report 0ms latency because the external validators measure model response time, not end-to-end agent execution. Timing comparisons only apply to Agents A--C.
\end{enumerate}

\subsection{Future Work}

Several directions emerge from this work:

\begin{enumerate}
  \item \textbf{Cross-model evaluation:} Expand simulated agents to use GPT-4, Claude, and Gemini as base models to test whether the security posture trends hold across architectures.
  \item \textbf{Adaptive attacks:} Develop payloads that evolve based on agent responses (e.g., multi-turn attacks that probe for weak points).
  \item \textbf{Real-time detection:} Integrate runtime injection detection that monitors both input and tool output streams during agent execution.
  \item \textbf{Full Gemma validation:} Re-run Agent D with sufficient API quota or a local deployment of the model to validate all 130 payloads.
  \item \textbf{Reproducibility infrastructure:} Extend the Sentra experiment platform to support automated cross-model comparison with standardized reporting.
\end{enumerate}

\subsection{Implications for Practitioners}
Our findings suggest that practitioners should: (1) implement multi-layered defenses rather than single filters; (2) restrict tool access to the minimum necessary set; (3) enforce iteration limits to prevent tool-loop exploits; and (4) validate security posture against multiple model families, as behavior varies significantly.

\section{Conclusion}
\label{sec:conclusion}

We presented a controlled experiment evaluating LLM agent security across 1,950 trials spanning 5 agents and 13 OWASP-aligned attack scenarios. Our results establish that comprehensive security postures achieve statistically significant improvements (40 percentage points, p < 0.05) over unprotected agents. External models showed higher baseline security, indicating that model architecture plays a critical role in injection resistance. All attack payloads and experiment code are open-sourced for reproducibility.
